# Project Purify Forensic Report Schema

Current schema version: `1.3.0`.

The report is deterministic for the same Project Purify build, Unicode datasets, input text, and normalized analysis options.

## Top-level fields

### `schemaVersion`

Version of the report contract. Consumers MUST check this before assuming field semantics.

### `tool`

```json
{
  "name": "Project Purify",
  "version": "0.8.0-dev"
}
```

The tool version is part of reproducibility. A report produced by a different version can legitimately differ even when the input hash is the same.

### `analysisOptions`

The normalized options actually used for analysis.

```json
{
  "clean": {
    "removeZeroWidthJoiner": false,
    "removeVariationSelectors": false,
    "normalize": "NFC"
  },
  "confusables": {
    "includeAscii": false
  },
  "scripts": {
    "languageHint": "auto",
    "profile": "prose",
    "strictMixedScript": false
  }
}
```

Consumers SHOULD preserve this object with the report. The same input can produce different policy findings when these options differ.

### `evidenceHashes`

SHA-256 digests of the UTF-8 encoded strings used by the report.

- `input`: original input text.
- `cleaned`: safe-cleaning output.
- `confusableSkeleton`: UTS #39-style skeleton output.

The hashes establish content identity. They do not establish authorship or origin.

### `dataProvenance`

Metadata for the Unicode datasets used by the build.

- `confusables`: source/version/integrity metadata for UTS #39 confusables.
- `scripts`: source/version/integrity metadata for Unicode `Scripts.txt`.

A fallback build can produce less complete findings than a build generated from the full pinned datasets. `completeness` records that distinction.

### `input`

Length metadata for the raw input:

- `utf16Length`: JavaScript/UTF-16 code-unit length.
- `codePointLength`: Unicode scalar/code-point iteration length.

See [OFFSETS.md](./OFFSETS.md) before mapping findings into editors or SARIF.

### `scriptAnalysis`

Records the mixed-script analysis profile, language hint, token count, and scripts observed.

### `summary`

Aggregate counts:

- `invisibleOrControlCount`
- `confusableCount`
- `mixedScriptCount`
- `highRiskCount`
- `changed`
- `severityCounts`
- `categoryCounts`

`highRiskCount` is a Project Purify policy result. It is not a probability and MUST NOT be interpreted as confidence that the text is AI-generated or malicious.

### `findings`

Three finding collections:

- `unicode`: invisible/format-control findings.
- `confusables`: reportable Unicode confusable findings.
- `mixedScripts`: token-level script-policy findings.

Each finding has a stable ID for a given input and analysis position. IDs are not globally stable identifiers across edited documents.

### `transformations`

- `cleanedText`: safe-cleaning output.
- `changes`: original-versus-cleaned change records.
- `confusableSkeleton`: comparison skeleton.

The skeleton is comparison data. A skeleton mapping by itself is not a suspicious finding.

### `limitations`

Human-readable limitations that apply to the report/build.

Consumers MUST NOT remove these limitations when presenting forensic results as evidence.

## Evidence interpretation

Project Purify is deterministic rule-based Unicode analysis.

It can support statements such as:

- “This input contains U+200B at this position.”
- “This token mixes Latin and Cyrillic characters.”
- “This build maps these characters to this confusable skeleton.”
- “Safe cleaning removed these format controls under these options.”

It does **not** support statements such as:

- “This text was generated by AI.”
- “The author intentionally inserted this character.”
- “This token is malicious.”
- “A high-severity finding proves deception.”

Attribution confidence is therefore intentionally **unsupported**. Consumers SHOULD present findings as deterministic text evidence plus explicit policy interpretation.

## Compatibility policy before v1.0

Report schema changes can occur during the `0.x` development series. Consumers SHOULD pin both Project Purify version and `schemaVersion`.

A stable migration/deprecation policy is a v1.0 release requirement.
